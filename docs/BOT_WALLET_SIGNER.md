# ตัวเซ็นกระเป๋าบอทแยกเครื่อง (Bot Wallet Signer)

> สถานะ 2026-11-13: **ติดตั้งขั้นที่ 1 แล้ว** บนเครื่องเชน 123.253.62.252 ที่ `/opt/tpix-bot-signer` (เจ้าของเลือกเครื่องนี้)
> container `tpix-bot-signer` รันอยู่ และรับคำขอเฉพาะจาก `127.0.0.1:8787` ของเครื่องนั้น — เครื่องเว็บยังต่อเข้ามาไม่ได้
> ยังไม่มีกระเป๋าจริง ยังไม่ได้เปิด `AIBOT_BOT_WALLET_ENABLED` บน production
>
> ค้างก่อนขั้นที่ 2 (เปิดให้เครื่องเว็บเรียก):
> 1. เจ้าของสำรอง `SIGNER_ENVELOPE_KEY` จาก `/opt/tpix-bot-signer/bot-signer/.env` ไว้นอกเครื่องด้วยตัวเอง
> 2. ปิดการล็อกอิน SSH ด้วยรหัสผ่านบนเครื่องเชน (ตอนนี้เครื่องนี้ถือคีย์ห่อแล้ว)
> 3. เปิดทางจากเครื่องเว็บ: ผูกพอร์ตกับ IP ของเครื่องเชนและอนุญาตเฉพาะต้นทาง 123.253.62.251 ใน `DOCKER-USER`
>    (สองเครื่องอยู่วง /24 เดียวกัน หน่วง 0.3 ms) หรือทำ WireGuard ระหว่างสองเครื่อง
> 4. โค้ดฝั่งเว็บ (branch นี้) ต้องขึ้น production แล้วตั้ง `AIBOT_BOT_WALLET_SIGNER*` ใน `.env` ของเว็บ
>
> ผลทดสอบบนเครื่องเชนหลังติดตั้ง (เรียกจากใน container ผ่าน loopback, ไม่มีธุรกรรมถูกส่งขึ้นเชน):
> ไม่มีลายเซ็น/secret ผิด → 401 · สร้างกระเป๋า → ได้ · สวอป `minOut=1` → `policy_min_out` (ตัวเซ็นถามราคาจาก BSC เองได้)
> · ถอน → เซ็นได้ ปลายทางคือเจ้าของ · ถอนไปที่อื่น → `policy_destination` · เปลี่ยนเจ้าของในคำขอ → `key_unreadable`
> · เหรียญนอกรายการ → `policy_token` · log ของ container ไม่มีกุญแจ · พอร์ต 8787 ต่อจากภายนอกไม่ได้
> กระเป๋าทดสอบถูกล้างออกจาก `state/wallets.jsonl` แล้ว (ไฟล์ว่าง ตัวนับเริ่มจากศูนย์)

## ปัญหาที่แก้

เครื่องเว็บ `tpix.online` (123.253.62.251) ตรวจเมื่อ 2026-11-13:

- มี 55 โดเมนใต้ผู้ใช้ระบบ `admin` ตัวเดียว และ php-fpm ทุก pool รันเป็น `admin`
- `admin` อยู่ในกลุ่ม `docker` และมี `sudo` แบบไม่ถามรหัสสำหรับ `tee` `cp` `sed` `cat` — เทียบเท่า root
- `.env` ของ tpix.online เป็นของ `admin` (สิทธิ์ 600) โค้ดของเว็บอื่นทั้ง 54 เว็บจึงอ่านได้

กุญแจกระเป๋าบอทแบบเดิมถูกห่อสองชั้น แต่ของที่ใช้ถอดทั้งสองชั้น (`APP_KEY` และ `AIBOT_BOT_WALLET_KEY`)
อยู่ใน `.env` ไฟล์เดียวกัน เว็บไหนในเครื่องถูกเจาะ คนร้ายถอดกุญแจกระเป๋าบอทได้ทุกใบ
การแยกผู้ใช้ระบบบนเครื่องเดิมไม่พอ เพราะ `admin` เทียบเท่า root อยู่แล้ว — **คีย์ห่อต้องไม่อยู่บนเครื่องนั้น**

## สิ่งที่เปลี่ยน

| | แบบเดิม (`local`) | แบบใหม่ (`remote`) |
|---|---|---|
| คีย์ห่อ | `.env` ของเครื่องเว็บ | `.env` ของเครื่องตัวเซ็นเท่านั้น |
| กุญแจส่วนตัวถูกสร้างที่ | เครื่องเว็บ | เครื่องตัวเซ็น |
| กุญแจส่วนตัวอยู่ในหน่วยความจำของ | เครื่องเว็บ (ตอนเซ็น) | เครื่องตัวเซ็นเท่านั้น |
| เครื่องเว็บเก็บ | ciphertext + คีย์ห่อ | ciphertext อย่างเดียว |
| ใครตัดสินว่าเซ็นอะไรได้ | เครื่องเว็บ | ตัวเซ็น (`policy.cjs`) ไม่เชื่อคำขอ |
| บน production | **ถูกปฏิเสธ** | ใช้ได้ |

แบบ `local` ยังอยู่เพื่อเทสต์และเครื่อง dev บน production ระบบจะถือว่ากระเป๋าบอทยังไม่เปิด
แม้จะตั้ง `AIBOT_BOT_WALLET_KEY` ไว้ก็ตาม เว้นแต่ตั้ง `AIBOT_BOT_WALLET_ALLOW_LOCAL_KEYS=true` เอง

## ถ้าเครื่องเว็บถูกยึดทั้งเครื่อง คนร้ายทำอะไรได้

คนร้ายได้ฐานข้อมูล (ciphertext) และ secret ที่ใช้เรียกตัวเซ็น จึงส่งคำขอได้ทุกรูปแบบ ตัวเซ็นยอมแค่นี้:

| คำขอ | ตัวเซ็นยอมให้ |
|---|---|
| ถอน | ปลายทางคือกระเป๋าเจ้าของเท่านั้น เจ้าของคือค่าที่ผูกกับ ciphertext (แก้ `owner_address` ในฐานข้อมูลแล้วถอดกุญแจไม่ออก) |
| สวอป | USDT ⇄ เหรียญในรายการของตัวเซ็น ผ่าน router ของ PancakeSwap ในรายการ เหรียญที่ได้กลับเข้ากระเป๋าเดิม |
| ราคา | `minOut` ต้องไม่ต่ำกว่าราคาที่ตัวเซ็นถามเชนเองเกิน 6% (ตั้ง `minOut = 1` เพื่อดักกินส่วนต่างไม่ได้) |
| ขนาด | ไม้เข้าไม่เกิน 500 USDT ต่อครั้ง |
| ความถี่ | 120 ลายเซ็นต่อกระเป๋าต่อวัน |

สิ่งที่คนร้ายยังทำได้ (ความเสียหายมีขอบเขต ไม่ใช่การขโมย):

- สั่งสวอปไปมาในเหรียญหลัก เสียค่าธรรมเนียมพูลและ slippage ภายในเพดานต่อวัน
- สั่งถอนเงินของผู้ใช้กลับเข้ากระเป๋าของผู้ใช้เอง
- ลบ ciphertext ในฐานข้อมูล — กู้ได้จาก `state/wallets.jsonl` บนเครื่องตัวเซ็น

สิ่งที่ตัวเซ็น **ไม่ได้** กัน: ราคาบนเชนที่ถูกบิดในบล็อกเดียวกัน (ตัวเซ็นเทียบกับราคาบนเชน ไม่มีราคาอ้างอิงนอกเชน)
ลดความเสี่ยงด้วยรายการเหรียญที่สภาพคล่องลึกและเพดานขนาดไม้ และถ้าเครื่องตัวเซ็นเองถูกยึด กุญแจทุกใบหลุด
เครื่องตัวเซ็นจึงต้องเป็นเครื่องที่รันของน้อยที่สุด

ต้องเป็นเครื่องที่ไม่ใช่ 123.253.62.251 และไม่รันเว็บของคนอื่น

| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| VPS ใหม่ขนาดเล็ก ใช้เฉพาะงานนี้ | แยกความเสี่ยงได้ดีที่สุด | มีค่าเช่า ต้องดูแลเพิ่มหนึ่งเครื่อง |

## ติดตั้ง

### 1. เครื่องตัวเซ็น

```bash
git clone <repo> && cd ThaiXTrade/scripts/blockchain/bot-signer
cp .env.example .env && chmod 600 .env
```

ใส่ค่าใน `.env`:

- `SIGNER_ENVELOPE_KEY` — `openssl rand -base64 48` **สำรองไว้นอกเครื่อง (ออฟไลน์) ทันที** หายหรือเปลี่ยน = กุญแจทุกใบถอดไม่ออก
- `SIGNER_HMAC_SECRET` — `openssl rand -base64 48` (คนละค่ากับคีย์ห่อ)
- `SIGNER_PUBLISH` — IP ของลิงก์ส่วนตัวถึงเครื่องเว็บ เช่น `10.8.0.2:8787` (เครื่องเว็บมี `wg` / `wg-quick` อยู่แล้ว)
- รายการเหรียญและสัญญา — รัน `php artisan aibot:signer-env` บนเครื่องเว็บ แล้วคัดลอกบรรทัดมาใส่

```bash
# โฟลเดอร์ state ต้องเป็นของ uid 1000 (ผู้ใช้ node ใน container) — ถ้าปล่อยให้ docker สร้างเอง จะเป็นของ root
# แล้วตัวเซ็นเขียนบันทึกกระเป๋าและตัวนับไม่ได้: สร้างกระเป๋าได้ 500 และไม่เซ็นให้เลยสักรายการ
mkdir -p state && sudo chown 1000:1000 state && chmod 700 state

docker compose up -d --build
docker compose logs --tail 5          # ต้องเห็น "listening on ... tokens=N"
curl -s http://<IP ลิงก์ส่วนตัว>:8787/health
```

พอร์ตที่ docker เปิดข้าม ufw — ผูก `SIGNER_PUBLISH` กับ IP ส่วนตัวเท่านั้น ห้ามใช้ `0.0.0.0`

### ขั้นที่ 2 — เปิดให้เครื่องเว็บเรียก (รันบนเครื่องตัวเซ็น ตามลำดับนี้เท่านั้น)

เครื่องเว็บกับเครื่องเชนอยู่วง /24 เดียวกัน จึงใช้ IP ของเครื่องเชนตรง ๆ และให้ไฟร์วอลล์รับเฉพาะต้นทางที่เป็นเครื่องเว็บ
ไฟล์ทั้งสองอยู่ใน `scripts/blockchain/bot-signer/` (บนเครื่องเชนวางไว้ที่ `/opt/tpix-bot-signer/bot-signer/` แล้ว)

```bash
cd /opt/tpix-bot-signer/bot-signer

# 1) ไฟร์วอลล์ก่อน — ถ้าเปิดพอร์ตก่อนใส่กฎ พอร์ตของตัวเซ็นจะเปิดสู่อินเทอร์เน็ต
sudo install -m 0755 tpix-signer-firewall /usr/local/sbin/tpix-signer-firewall
sudo install -m 0644 tpix-signer-firewall.service /etc/systemd/system/tpix-signer-firewall.service
sudo systemctl daemon-reload && sudo systemctl enable --now tpix-signer-firewall.service
sudo tpix-signer-firewall status          # ต้องเห็นกฎ tpix-signer-webonly

# 2) แล้วค่อยเปิดพอร์ตบน IP ของเครื่อง
sudo sed -i 's|^SIGNER_PUBLISH=.*|SIGNER_PUBLISH=123.253.62.252:8787|' .env
sudo docker compose up -d
```

ตรวจ: จากเครื่องเว็บ `curl -s http://123.253.62.252:8787/health` ต้องตอบ `{"ok":true,...}`
และจากเครื่องอื่นใดต้องต่อไม่ติด ถอยกลับ: ตั้ง `SIGNER_PUBLISH=127.0.0.1:8787` แล้ว `sudo docker compose up -d`

### เครื่องเว็บ

เพิ่มใน `.env` ของ tpix.online แล้ว `php artisan config:cache`:

```
AIBOT_BOT_WALLET_SIGNER=remote
AIBOT_BOT_WALLET_SIGNER_URL=http://<IP ลิงก์ส่วนตัวของเครื่องตัวเซ็น>:8787
AIBOT_BOT_WALLET_SIGNER_SECRET=<ค่าเดียวกับ SIGNER_HMAC_SECRET>
```

ห้ามใส่ `AIBOT_BOT_WALLET_KEY` บนเครื่องเว็บ production

```bash
php artisan aibot:signer-env          # ต้องขึ้น remote / ตั้งครบ: ใช่ / ตัวเซ็นตอบ: ใช่
```

### 3. ทดสอบก่อนเปิดให้ผู้ใช้

เปิด `AIBOT_BOT_WALLET_ENABLED=true` (ยังไม่เปิด `AIBOT_LIVE_EXECUTION`) แล้วเจ้าของทดสอบด้วยกระเป๋าตัวเอง:

1. สร้างกระเป๋าบอท — ที่ `state/wallets.jsonl` บนเครื่องตัวเซ็นต้องมีบรรทัดใหม่ และแถวใน `ai_bot_wallets` ต้องเป็น `key_version = 2`
2. ฝาก USDT เล็กน้อยกับ BNB ค่าแก๊ส แล้วถอนกลับ — ธุรกรรมบนเชนต้องมีปลายทางเป็นกระเป๋าเจ้าของ
3. จึงค่อยเปิด `AIBOT_LIVE_EXECUTION` และทดสอบไม้จริงขนาดขั้นต่ำหนึ่งรอบ

## สำรองและกู้คืน

| ของ | อยู่ที่ | ถ้าหาย |
|---|---|---|
| `SIGNER_ENVELOPE_KEY` | `.env` ของเครื่องตัวเซ็น + สำเนาออฟไลน์ | กุญแจทุกใบถอดไม่ออก เงินในกระเป๋าบอทติดถาวร |
| ciphertext | ฐานข้อมูลของเว็บ (`ai_bot_wallets.key_ciphertext`) + `state/wallets.jsonl` | กู้จากอีกที่หนึ่ง |
| `SIGNER_HMAC_SECRET` | สองเครื่อง | สร้างใหม่ ใส่สองฝั่ง แล้วรีสตาร์ตตัวเซ็น |

สำรอง `state/wallets.jsonl` ออกนอกเครื่องตัวเซ็นเป็นรอบ ไฟล์นี้ไม่มีกุญแจที่อ่านได้ (เป็น ciphertext)

## เมื่อตัวเซ็นล่ม

- สร้างกระเป๋าใหม่ไม่ได้ ผู้ใช้เห็นข้อความว่าระบบไม่พร้อมชั่วคราว ไม่มีกระเป๋าครึ่ง ๆ กลาง ๆ เกิดขึ้น
- รายการถอนและคำสั่งเทรดที่ถึงคิวจะกลับเข้าคิวและลองใหม่ทุกนาที คำสั่งเทรดที่ค้างเกินอายุถูกปิดตามปกติ
- **ไม้ที่เปิดอยู่จะปิดไม่ได้จนกว่าตัวเซ็นกลับมา** — ควรเฝ้า `/health` ของตัวเซ็นและแจ้งเตือนเมื่อไม่ตอบ
- ระบบไม่ถอยกลับไปใช้คีย์ห่อบนเครื่องเว็บเอง ไม่ว่ากรณีใด

## ยังไม่ได้ทำ / ยังไม่ได้ทดสอบ

- เปิดทางระหว่างเครื่องเว็บกับเครื่องตัวเซ็น และทดสอบการเรียกข้ามเครื่อง (ขั้นที่ 2)
- ธุรกรรมจริงบนเชนผ่านตัวเซ็น (ทดสอบแล้วแค่ให้ตัวเซ็นจริงเซ็นธุรกรรมถอนของกระเป๋าเปล่าโดยไม่ส่งขึ้นเชน
  และให้ปฏิเสธสวอปที่ `minOut` ต่ำจากราคาจริงบน BSC)
- การแจ้งเตือนเมื่อตัวเซ็นไม่ตอบ และการสำรอง `wallets.jsonl` อัตโนมัติ
- กุญแจของกระเป๋าร้อนตัวอื่นบนเครื่องเว็บ (คลัง สะพาน ตัวรักษาราคา) ยังอยู่บนเครื่องเดิม — เอกสารนี้ครอบเฉพาะกระเป๋าบอท
